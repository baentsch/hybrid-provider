# Contributing to hybrid-provider

Guidance for working on the provider itself. If you only want to *use* it, see
the [README](README.md) and [USAGE.md](USAGE.md).

## AI contributions

This provider is AI-generated by design (see the note in the
[README](README.md)), and it is **not** intended for productive use. In keeping
with that:

- **AI-assisted contributions are explicitly welcome** — indeed encouraged. There
  is no expectation that code here be written by hand; using an AI coding
  assistant to prepare a change is a first-class way to contribute.
- **AI may be used to evaluate pull requests.** Submissions may be reviewed with
  the help of AI tooling in addition to a human reviewer. Expect automated review
  feedback and feel free to address it the same way you would a human reviewer's
  comments.

The provider is developed in close collaboration between its maintainer(s) and an
AI coding assistant — this is the project's method by design. Whatever tools are
used, the bar for merging is unchanged: the change must be correct, keep the test
suite green, and keep the docs in step with the code. Every contribution —
including AI-generated code — has been and will continue to be reviewed and
approved by a human maintainer before it is merged; AI tooling may assist that
review but never replaces it, and a human maintainer is accountable for each
change that lands. This is development review for correctness, test coverage and
design fit — **not** a formal security audit, and it does not change the
project's "not for production use" status (see [SECURITY.md](SECURITY.md)).

## Getting started

- Build the provider as described in the [README](README.md#build). A dev build
  is the same build — there is no separate developer configuration.
- Run the test suite (`ctest`) before and after your change; see
  [TESTING.md](TESTING.md) for the full inventory, the cross-provider interop
  matrix, the CLI harness and the benchmark.
- Read [design.md](design.md) for the architecture and the reasoning behind the
  EVP-only, provider-agnostic design — it is the reference for *why* things are
  shaped the way they are.

## Code conventions

- C11, targeting Linux.
- OpenSSL coding style (4-space indent, K&R braces).
- All public symbols prefixed with `hybrid_` (composite family: `composite_`).
- Error handling via `ERR_raise` / `ERR_raise_data`.
- **EVP-only.** All cryptographic operations delegate to sub-algorithms via the
  public EVP API — no internal OpenSSL headers. This is the central invariant of
  the project; a change that reaches into libcrypto internals does not belong
  here.
- Keep quirks documented with short inline comments and a source reference,
  rather than long prose elsewhere.

## Security conventions

This is cryptographic code that parses untrusted key material, so contributions
follow the secure-coding principles in the OpenSSF [Security-Focused Guide for AI
Code Assistant Instructions](https://best.openssf.org/Security-Focused-Guide-for-AI-Code-Assistant-Instructions).
The guide is the reference; the concrete expectations that already hold here are:

- **Validate untrusted input.** Bounds-check every wire length before splitting a
  DER/SPKI/PKCS#8 blob or copying from it; never trust a length field blindly.
- **Wipe secrets.** Zero private-key and shared-secret buffers on *every* exit
  path (`OPENSSL_cleanse` / `OPENSSL_clear_free` / `OPENSSL_secure_clear_free`).
- **No secrets in diagnostics.** `ERR_raise*` strings and logs carry algorithm
  names and public lengths only — never key or secret bytes.
- **Test the failure paths**, not just the happy path — negative decode tests and
  the decoder fuzz harness (`-DHYBRID_FUZZ`) are part of that contract.
- Dynamic analysis (ASan/UBSan/TSan, libFuzzer) is the primary safety net; CI also
  builds hardened (`-DHYBRID_HARDEN=ON`) as a static complement.

**Deliberately out of scope.** The guide's production supply-chain and
release-integrity controls — SBOM generation (SPDX/CycloneDX), SLSA/in-toto
provenance, SHA-pinning of CI actions and dependencies, and a SAST gate
(CodeQL/Semgrep) — are *not* adopted here on purpose. This provider carries
pre-standardization algorithms for interoperability experiments and is explicitly
not production-destined (see [README.md](README.md) / [design.md](design.md));
development velocity and the freedom to track fast-moving upstreams (OpenSSL,
liboqs, oqsprovider — some legs deliberately float to `main`) matter more than
those checkbox controls, and the dynamic-analysis suite above is the chosen
primary assurance. Revisit this decision if the provider is ever hardened toward
production use.

## Project layout

The source is a flat set of dispatch files, one per provider operation.
[design.md](design.md#build-system) lists every file; the key ones:

| File | Responsibility |
|---|---|
| `hybrid_prov.{c,h}` | provider init, `query_operation`, shared types + the algorithm tables |
| `hybrid_keymgmt.c` | keymgmt dispatch (hybrid keys) |
| `hybrid_kem.c` | KEM dispatch (encaps/decaps) |
| `hybrid_sig.c` | signature dispatch (sign/verify) |
| `hybrid_caps.c` | TLS-GROUP + TLS-SIGALG capability advertising |
| `hybrid_{encoder,decoder}.c` | SPKI/PKCS8 key encoders/decoders |
| `composite_*.{c,h}` | composite (LAMPS) family, only with `-DHYBRID_COMPOSITE` |

## Adding a hybrid algorithm

The algorithm inventory is **table-driven** — those tables are the single source
of truth for names, OIDs and TLS code points:

- KEMs / signatures — `HYBRID_KEM_LIST` / `HYBRID_SIG_LIST` in `hybrid_prov.h`
- composite signatures — `COMPOSITE_SIG_LIST` in `composite_prov.h`
- composite KEMs — `COMPOSITE_KEM_LIST` in `composite_kem_prov.h`

Adding a hybrid is normally a table entry plus its component wiring; see
[design.md → Algorithm Configuration](design.md#algorithm-configuration) for how
the tables drive keymgmt, KEM/sig dispatch and capability advertising. Update the
inventory tables in the [README](README.md#supported-algorithms) to match, and
add coverage to the relevant test.

### Step by step

Self-contained recipe for one new hybrid KEM or signature. Component sizes are
compile-time constants (not computed at runtime), so a new row needs a matching
size row — which you do **not** hand-count: a generator derives them from live
component keygens.

1. **Add the master-list row** in `hybrid_prov.h` — `HYBRID_SIG_LIST` for a
   signature, `HYBRID_KEM_LIST` for a KEM. Each row's `X(...)` field order is
   documented in the comment directly above the list. The component names
   (`alg1` / `alg2`) are the EVP fetch names their provider registers (e.g.
   `"MLDSA65"`, `"snova2454"`, `"CROSSrsdp128balanced"`); a classical EC half
   carries its curve in `alg1_group` / `alg2_group`, everything else is `NULL`.
   For identifiers, follow
   [Experimenting with a provider-private combination](#experimenting-with-a-provider-private-combination-no-interop-peer)
   below: operation-only (`NULL` OID, code point `0`) to start, or private-use
   identifiers to make it serialize/negotiate.
2. **Add a placeholder size row** at the **same ordinal** in the matching array
   (`hybrid_sig_sizes[]` / `hybrid_kem_sizes[]`, just below the list) — the index
   is positional (`HYBRID_*_IDX_*`), so it must line up with your new list row:

   ```c
   { 0 },   /* snova2454_crossrsdp128balanced */   /* filled in step 4 */
   ```
   The `{ 0 }` is just a placeholder; step 4 fills it with the real, emitted form:
   a `HYBRID_SIZES` row is nested per logical component —
   `{ { {pub, prv, ss, ct, sig}, {pub, prv, ss, ct, sig}, … } }`, one inner
   `HYBRID_COMP_SIZES` per component (KEMs populate `ss`/`ct` with `sig == 0`;
   signatures populate `sig` with `ss == ct == 0`). A three-component row simply
   carries a third inner brace. You never hand-count these — see step 4.
   (A non-concatenation KEM additionally needs a `hybrid_kem_combiner[]` entry —
   see the combiner note above.)
3. **Build the provider**, with the component providers reachable. If a component
   lives in oqsprovider (any non-ML-DSA/ML-KEM PQ family: Falcon, MAYO, SNOVA,
   CROSS, UOV, MQOM, Frodo, BIKE, HQC), put an oqsprovider built against the
   *same* OpenSSL on the module path — `./test/setup_oqs_interop.sh` builds and
   symlinks one into the build dir. Without it the new row self-skips
   "component provider absent" (and the generator can't resolve its sizes).

   ```sh
   cmake --build build -j4
   ```
4. **Generate the real sizes** and paste them over the placeholder. From the
   build dir, `emit` re-derives every row from live keygens and prints both size
   tables as C initializers:

   ```sh
   cd build
   OPENSSL_MODULES=$PWD ./hybrid_sizes_test emit     # add LD_LIBRARY_PATH=<ossl>/lib64 if needed
   ```
   Copy the line for your new algorithm (a row that printed `{ 0 } ... UNRESOLVED`
   means its components were not fetchable — fix step 3 first) back into the array
   from step 2, then rebuild.
5. **Verify.** The table-driven tests pick the row up automatically:
   `hybrid_sizes_test` goes green once the sizes match (it fails CI on any drift);
   `hybrid_leakcheck_test` round-trips it in-provider (keygen / sign-verify or
   encaps-decaps / SPKI+PKCS8 encode→decode→`eq`); a non-zero code point pulls it
   into `hybrid_cert_tls_test`, an OID into `hybrid_cms_test`, and both into
   `hybrid_capability_test`.

   ```sh
   ctest
   ```
6. **Update the README counts and inventory tables**
   ([Supported algorithms](README.md#supported-algorithms)); `hybrid_count_test`
   fails the suite until the counts match the tables.

A hybrid KEM whose shared secret is **not** the plain concatenation of the
component secrets (the RFC 10024 default) selects a combiner in
`hybrid_kem_combiner[]` (next to `hybrid_kem_sizes[]` in `hybrid_prov.h`), keyed
by the row's `HYBRID_KEM_IDX_*`. The combiner code in `hybrid_kem.c` is
**component-agnostic** — it reads every segment length from the key's size row —
so:

- **Same combiner, different components** (e.g. an X-Wing-style KEM over ML-KEM-1024
  or an experimental KEM) is **two table lines only**: a `HYBRID_KEM_LIST` row and
  a `hybrid_kem_combiner[]` entry. No combiner-code change. The `xwing_*`
  experimental rows are the worked examples; `hybrid_leakcheck_test` already
  round-trips every KEM row in-provider (keygen/encaps/decaps with shared-secret
  match, over `HYBRID_KEM_ALG_COUNT`), so a new row is covered automatically.
- **A genuinely new combiner** adds a `HYBRID_COMBINER_*` value and its own
  combine function in `hybrid_kem.c` (alongside `hybrid_xwing_combine`), invoked
  from the encaps/decaps combiner branch.

X-Wing (`draft-connolly-cfrg-xwing-kem`, a SHA3-256 strongly-binding combiner) is
the standards-backed instance — additionally pinned by a KAT against the draft's
reference vectors (`xwing_kat_test`) with a weekly vector-coherence guard
(`scripts/check-xwing-kat-drift.sh`).

### Three or more components (concat only)

The concatenation combiner is N-ary (issue #135), so a KEM may list up to
`HYBRID_MAX_COMP` (4) components — the draft-preussmattsson-tls-hqckem PQ/PQ/T
groups (`HQCKEM192MLKEM768X25519`, `HQCKEM256MLKEM1024X448`) are the worked
three-component examples. Such a row uses the `X3` generator (`HYBRID_KEM_ROW_3`)
instead of `X(...)`, listing its components in **logical** order followed by an
explicit `wire[]` permutation (logical indices in concatenation order) — see the
comment above `HYBRID_KEM_LIST`. The size row is the same nested per-component
form (below) with one more component entry; `n_comp` is derived from the
descriptor, so nothing else changes. The strongly-binding combiners (X-Wing) stay
two-component and assert `n_comp == 2` — N applies to concat only. Beyond keygen /
encaps / decaps and the raw `ENCODED_PUBLIC_KEY` key share, each component of an
N>2 row is individually extractable through the indexed `hybrid-comp{i}-pub-spki`
/ `-priv-pkcs8` params (`hybrid_extract_test`); two-component rows additionally
keep the role-based `hybrid-classic-*` / `hybrid-pq-*` names. N>2 rows are
operation-only (no key-file OID), as the combined SPKI/PKCS8 format holds exactly
one classical + one PQ component (see [design.md](design.md#operation-kem)).

### Experimenting with a provider-private combination (no interop peer)

A first principle of this provider: **any component reachable through the public
EVP API can be paired with any other, from any provider.** The hybrid code never
touches the raw cryptography — it orchestrates the components over EVP and is
agnostic to which provider implements them (steer each slot with
`alg1-propquery` / `alg2-propquery`; see
[USAGE.md](USAGE.md#selecting-component-providers-alg1-propquery--alg2-propquery),
where sourcing a hybrid's PQ half from
[wolfProvider](https://github.com/wolfSSL/wolfProvider) is a worked example). So
experimenting with a pairing no standard defines and no other provider serves is
deliberately cheap.

Such a combination has **no interop peer**, so do not invent — or reuse — a
standardized identifier for it. Two levels, cheapest first:

- **Operation-only.** Leave the row's `oid` `NULL` and its TLS code point `0`. The
  combination can be keygen'd, signed/verified or encaps/decaps'd and KAT-checked,
  but is not serializable (no X.509/PKCS8/CMS) or TLS-negotiable. This is the
  smallest possible experiment — one table line (plus a `hybrid_kem_combiner[]`
  entry for a non-concatenation KEM).
- **Serializable / TLS-negotiable.** Give it **private-use** identifiers: an OID
  in this provider's `1.3.9999.99.*` arc and a TLS code point in the private-use
  range (`0xFE00..0xFFFF` — signatures use the `0xFFE5..` sub-block after the
  composite rows; KEMs the NamedGroup private-use space). **Never shadow a
  standardized identifier**; `hybrid_capability_test` enforces that every code
  point sits in a known IANA-assigned span or a provisional/private-use range.
  The `xwing_*` KEM rows (operation-only) and the §3.4 signature rows
  `mldsa65_falcon1024` / `mldsa44_mayo1` / `falcon512_mayo1` / `mldsa65_p256`
  (private-use, issue #126) are the worked examples.

For **signatures** the sign/verify path, the construction, and the private-key
serialization are all **slot-symmetric** (issues #114 / #125 / #126), so either
slot may be classical (ECDSA/RSA, with its curve on `alg1_group` / `alg2_group`)
or md-less PQ, in either order, with no code change. For a **PQ/PQ** signature
`nist_level` no longer selects a digest; set it to the **min** of the two
components' NIST categories — the advertised TLS security bits, the weaker
survivor if one scheme is broken (see [STANDARDS.md §3.4](STANDARDS.md)).

The table-driven tests then pick the row up automatically: `hybrid_leakcheck_test`
round-trips it in-provider (keygen / sign-verify / SPKI+PKCS8 encode→decode→`eq`);
a non-zero code point pulls it into `hybrid_cert_tls_test`, and an OID into
`hybrid_cms_test`. Cross-provider tests (`hybrid_encode_test`,
`hybrid_matrix_test`, `hybrid_coexist_test`) skip a row by probing whether another
provider actually serves the name — not by whether it has an OID — so a
provider-private row is correctly left out of the interop sweep.

A fully **config-declared** form — arbitrary pairings at runtime with no table
edit or rebuild — is the planned "define-a-hybrid" mechanism, tracked in
[#112](https://github.com/baentsch/hybrid-provider/issues/112).

### The oqsprovider coverage invariant

Every OQS-legacy hybrid must match
[oqsprovider](https://github.com/open-quantum-safe/oqs-provider) byte-for-byte,
and **every hybrid oqsprovider advertises must also be served here.** This is
enforced two ways (both described in [TESTING.md](TESTING.md)):

- `hybrid_coverage_test` — fails the suite at test time against a built
  [oqsprovider](https://github.com/open-quantum-safe/oqs-provider).
- `scripts/check-oqs-hybrid-drift.sh` plus the weekly
  `.github/workflows/oqs-hybrid-drift.yml` — a buildless source diff that opens a
  tracking issue when upstream adds a hybrid this provider does not yet serve.

If you are resolving such a drift issue, adding the missing hybrid to the tables
above is the fix.

## Submitting changes

Open a pull request against
[`baentsch/hybrid-provider`](https://github.com/baentsch/hybrid-provider). Keep
`ctest` green (including the composite and oqsprovider-interop tests when their
prerequisites are present), and keep the docs in step with the code — the tables,
the README inventory and design.md are expected to agree.

All participants are expected to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
