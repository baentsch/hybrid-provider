# Cross-provider interoperability & performance

Interoperability proof and side-by-side performance for the hybrid provider
against **multiple external providers serving the same PQ primitives**, all
loaded into one process on OpenSSL master:

| Provider | Role here | Serves |
|---|---|---|
| **default** (OpenSSL master, 4.2.0-dev, 13 Oct 2026) | native PQ + native MLX hybrids | ML-KEM-512/768/1024, ML-DSA-44/65/87, MLX hybrids |
| **wolfProvider** (1.2.2, wolfSSL master, `--enable-mlkem --enable-mldsa`) | native PQ + native MLX hybrids | ML-KEM-512/768/1024, ML-DSA-44/65/87, X25519MLKEM768 / SecP256r1MLKEM768 / SecP384r1MLKEM1024 |
| **mldsa-native-provider** (mldsa-native v2.0.0) | native ML-DSA only | ML-DSA-44/65/87 |
| **hybrid-provider** (this repo) | composes hybrids & composites from any of the above | all hybrid KEMs/sigs + composites |

The hybrid provider is **EVP-only**: it composes its PQ half from whichever
provider the property query selects, so each of default / wolfProvider /
mldsa-native-provider can serve as the PQ component source.

Generated by `test/provider_matrix` (CMake target `provider_matrix`); raw output
in the appendix. All timings are the **minimum per-op latency** over a 300 ms
budget (noise only adds time), single-threaded on this machine.

## Reproduce

```sh
# 1. wolfProvider + its OpenSSL master + wolfSSL master (LC_ALL=C avoids a
#    locale bug in the version stamp; see below)
cd wolfprovider
WOLFSSL_TAG=master OPENSSL_TAG=master LC_ALL=C LANG=C \
  ./scripts/build-wolfprovider.sh --openssl-ver=master --enable-mlkem --enable-mldsa
make libwolfprov.la      # the lib builds clean; only the unit tests trip -Werror on master
mkdir -p wolfprov-install/lib
cp .libs/libwolfprov.so.0.0.0 wolfprov-install/lib/libwolfprov.so
OSSL=$PWD/openssl-install
ln -sfn lib64 $OSSL/lib   # master installs to lib64; find_package looks in lib

# 2. mldsa-native-provider and hybrid-provider against that same OpenSSL master
for repo in ../mldsa-native-provider .; do
  cmake -S $repo -B $repo/build-wolf -DOPENSSL_ROOT_DIR=$OSSL \
    -DOPENSSL_CRYPTO_LIBRARY=$OSSL/lib64/libcrypto.so \
    -DOPENSSL_SSL_LIBRARY=$OSSL/lib64/libssl.so -DOPENSSL_INCLUDE_DIR=$OSSL/include
  cmake --build $repo/build-wolf -j
done

# 3. gather the sibling modules onto the hybrid build dir's module path and run
cd <hybrid-provider>/build-wolf
ln -sf $OSSL/../wolfprov-install/lib/libwolfprov.so .
ln -sf ../../mldsa-native-provider/build-wolf/mldsanative.so .
LD_LIBRARY_PATH=$OSSL/lib64:$OSSL/../wolfssl-install/lib \
  OPENSSL_MODULES=$PWD ./provider_matrix 300
```

Build gotchas worth remembering: wolfProvider's version stamp uses `date '+%b'`
and fails OpenSSL `Configure` under a non-English locale (`LC_ALL=C`); its unit
tests (not the library) fail `-Werror=discarded-qualifiers` on master; and
`find_package(OpenSSL)` pairs master's headers with the *system* libcrypto
unless `lib64` is bridged and the library paths are passed explicitly.

## A. Interoperability — all cross-provider checks pass

**ML-DSA, sign × verify (every provider pair).** A key + signature produced by
the row provider, verified by the column provider (OpenSSL re-imports the key
across providers automatically). Identical for ML-DSA-44/65/87:

| sign ╲ verify | default | wolfProvider | mldsa-native |
|---|---|---|---|
| **default** | OK | OK | OK |
| **wolfProvider** | OK | OK | OK |
| **mldsa-native** | OK | OK | OK |

**ML-KEM, encaps/decaps (shared-secret equality).** Key + ciphertext from the
row provider, decapsulated by the column; cell = shared secrets match.
Identical for ML-KEM-512/768/1024:

| encaps ╲ decaps | default | wolfProvider |
|---|---|---|
| **default** | OK | OK |
| **wolfProvider** | OK | OK |

**Hybrid-KEM wire compatibility.** The hybrid provider's *composed* key, via
public-key export/import, interoperates **both directions** with the native MLX
groups of default and wolfProvider:

| Hybrid group | vs default | vs wolfProvider |
|---|---|---|
| X25519MLKEM768 | OK / OK | OK / OK |
| X448MLKEM1024 | OK / OK | — (not served) |
| SecP256r1MLKEM768 | OK / OK | OK / OK |
| SecP384r1MLKEM1024 | OK / OK | OK / OK |
| SecP256r1MLKEM512 | OK / OK | — (not served) |

(“native-encaps/hybrid-decaps” and “hybrid-encaps/native-decaps” both pass.)
mldsa-native-provider serves no KEM, so it does not appear in the KEM rows.

wolfProvider is ~4–7× and mldsa-native-provider ~6× faster than OpenSSL master's

are implementation differences in the three independent FIPS-203/204 cores, not
anything the hybrid provider does.)

## C. Hybrid & composite performance, PQ component per provider

Same budget. The classical half is pinned to the default provider; **only the PQ
component's provider varies between rows of the same algorithm.** Keygen for the
RSA-classical combos is dominated by RSA key generation (classical, hence
identical crypto across the three rows) and is heavy-tailed, so treat those
keygen numbers as noise — the **sign/verify** and **encaps/decaps** columns are
the meaningful signal.

## Notes & caveats

- **Min-latency model** (shared with the repo's other benches): each timing is
  the minimum per-op over a budgeted run; noise only adds time. Numbers are
  machine- and build-specific — rerun locally for your own figures.
- **Classical half is pinned to the default provider** in C (via the hybrid
  provider's `classic-propquery`), so a composed row isolates the PQ provider's
  contribution. Pure RSA/EC keygen is not attributable to the PQ provider; the
  RSA-combo keygen figures are included for completeness but are RSA-bound and
  heavy-tailed.
- **Coverage.** wolfProvider serves ML-KEM-512/768/1024 and ML-DSA-44/65/87 and
  three MLX hybrids (X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024);
  mldsa-native-provider serves ML-DSA only. Rows a provider cannot serve are
  skipped, not failed.
- The hybrid provider composes the *same* primitive the peer measures, so its
  composition overhead over the sum of components is tracked separately by
  `hybrid_bench` / `composite_*_bench`; this document is about cross-provider
  interop and the relative speed of the PQ cores.
